# Lifelikegame 开发变更 SOP

## 1. 目的

本 SOP 规定 Lifelikegame 路线图任务的分析、确认、修改、验证和交付方式。
目标是让每项变更都有明确原因、受控范围和可追溯结果，避免跳过依赖、擅自扩大
范围，或在没有验证证据时宣称功能已经正确。

本 SOP 是后续 Phase 工作的默认协作方式。用户在当前对话中的明确指示始终具有
更高优先级。

## 2. 角色与责任

### 用户

- 决定要推进的 Phase 和任务。
- 审核每项任务的原因、方案、范围和风险。
- 明确批准后，Codex 才能修改程式。
- 负责 `git add`、commit、push、合并和发布。
- 在具备环境时执行应用、手动验收或完整测试。

### Codex

- 读取路线图和仓库现况。
- 在修改前解释为什么要做以及准备如何修改。
- 等待用户明确确认后再改程式。
- 使用代码知识图检查实现位置、调用关系和影响面。
- 保持变更局部，不擅自加入其他 Phase 的工作。
- 按约定执行可用验证，并准确说明未验证的部分。
- 不执行 Git 写入、push、合并或发布，除非用户另行明确授权。

## 3. 工作依据

开始路线图工作前，必须先读取：

```text
Lifelikegame_Phase_Progress_Tracker_CN.xlsx
```

读取时至少确认：

- 当前 Phase 的目标。
- 当前任务的 ID、分类、优先级和难易度。
- 是否属于“上线前必须完成”。
- 任务的计划行动与完成／测试标准。
- 主要影响范围。
- 前置依赖任务。
- `Production Gate` 中对应的上线条件。
- `Design Rules` 中适用于本任务的架构原则。

如果路线图与仓库现况不一致，先向用户说明差异，不直接按过时内容修改。

## 4. Phase 顺序

默认遵循以下层级：

- Phase 1–7：当前小规模上线前需要推进。
- Phase 8：Backend 稳定后再做。
- Phase 9：有真实用户和重要资料后再做。

不得为了“顺便完善架构”而提前实施 Phase 8 或 Phase 9。任务存在依赖时，应先
完成依赖，或明确说明为什么暂时跳过。

## 5. 每项任务的标准流程

### 步骤 1：确认任务

Codex 必须说明：

- 当前要做的是哪个 Phase、哪个任务 ID。
- 任务名称是什么。
- 是否存在尚未完成的依赖。
- 本次是否只处理该任务。

如果用户使用“下一项”“阶段 5”等可能有多种解释的表达，应结合上下文给出
明确解释；若错误解释会造成明显风险，必须先询问。

### 步骤 2：检查仓库现况

仓库存在 `.codegraph/` 时，代码探索优先使用 CodeGraph。项目使用
codebase-memory-mcp 时，也应优先使用其图工具。

优先次序：

1. CodeGraph：读取相关符号、源码、调用路径和影响面。
2. codebase-memory-mcp：查找符号、调用者、实现和架构关系。
3. `rg`：仅用于配置、字符串、错误讯息和非代码文件，或图工具资讯不足时。
4. 直接读取文件：仅用于图工具未覆盖的明确细节。

检查内容至少包括：

- 当前实现。
- 谁调用该实现。
- Response、Schema、Interface 和前端消费方式。
- 环境变量及 CI 配置。
- 是否已有测试覆盖。
- 是否存在用户尚未提交的相关修改。

不得覆盖或清理不属于当前任务的用户变更。

### 步骤 3：修改前说明

在修改任何程式前，Codex 必须先向用户说明以下内容。

#### 为什么要做

- 当前行为有什么问题。
- 问题会造成什么实际影响。
- 为什么该任务属于当前 Phase。

#### 准备怎么改

- 修改哪些文件。
- 资料或调用流程会如何改变。
- API、数据库或前端契约是否改变。
- 哪些内容明确不在本次范围内。

#### 风险与验证

- 可能影响哪些调用者。
- 是否新增依赖、环境变量或数据库 Migration。
- 可以执行哪些验证。
- 哪些行为因为环境限制而无法验证。

说明完成后必须等待用户明确同意。没有确认，不修改程式。

### 步骤 4：控制范围

实施时遵守：

- 只修改已批准的文件和行为。
- 使用最小、可读的改动。
- 不顺便格式化整份文件。
- 不顺便重构无关模块。
- 不顺便修复其他 Phase 的问题。
- 不新增依赖，除非事先解释理由、版本锁定影响和替代方案，并取得批准。
- 不更改 API 契约，除非事先说明前端和调用者影响。
- 不修改数据库结构，除非已包含 Migration、回滚和验证方案，并取得批准。

若探索过程中发现方案必须扩大范围，应停止修改并重新向用户说明。

### 步骤 5：实施修改

修改时：

- 使用 `apply_patch` 编辑文件。
- 保留项目现有命名和架构风格。
- 依据 `Design Rules` 维持层级边界。
- 安全配置不得提供公开或弱默认 Secret。
- 日志不得输出密码、hash、JWT、Token、API Key 或其他敏感资料。
- Ledger 只记录真实业务事件，不建立无意义的零变化记录。
- Response 应使用交易完成后的资料来源，而不是可能过期的旧对象。

### 步骤 6：验证

验证级别由用户授权和环境能力决定。

#### 完整验证可用时

按风险执行：

- 新增或更新自动化测试。
- 先观察测试因缺少修正而失败，再实施最小修正。
- 执行目标测试。
- 执行相关测试集。
- 必要时执行完整测试、静态类型检查或 linter。
- 检查 `git diff --check`。
- 审查完整 scoped diff。

只有看到最新测试输出为通过，才能说“测试通过”。

#### 用户要求不执行测试时

不得运行：

- pytest 或其他测试套件。
- 应用服务器。
- 数据库 Integration Test。
- API 手动请求。
- 会触发真实 AI、Scheduler 或外部服务的操作。

可以按用户批准执行：

- Python 语法解析。
- 静态代码和调用关系检查。
- `git diff --check`。
- scoped diff 审查。

交付时必须明确写出：

```text
未执行测试或运行应用；目前只通过语法与差异检查。
```

语法检查不代表运行时、数据库、API 或业务行为正确。

### 步骤 7：处理 CI 失败

CI 失败时先调查根因，不直接修改。

依序检查：

1. 完整错误和 stack trace。
2. 失败发生在安装、collection、测试、build 还是部署阶段。
3. 最近变更与失败位置的关系。
4. CI workflow 提供的环境变量。
5. 测试 `conftest` 和应用 import 顺序。
6. 本机与 CI 的 Python、依赖、数据库和环境差异。
7. 警告与真正错误是否有关。

必须区分：

- 测试失败。
- pytest collection 失败。
- 应用 import／启动失败。
- CI 配置错误。
- 依赖或版本问题。

确认根因后，先向用户解释原因和最小修复，再取得确认。

例如 Backend 读取 `JWT_SECRET`，CI 却只设置 `SECRET_KEY` 时，属于 CI 环境变量
名称不一致；不是业务测试失败。

### 步骤 8：交付

完成后应说明：

- 修改了什么。
- 为什么新行为更正确。
- 修改的文件和关键位置。
- 已执行哪些验证及其结果。
- 哪些测试或行为没有验证。
- 是否有前端、CI、环境变量或部署注意事项。
- 建议的下一项任务。

不得使用“已经完全修好”“全部通过”等超出证据的说法。

### 步骤 9：Git 交接

默认由用户负责：

- `git add`
- `git commit`
- `git push`
- Pull Request
- merge
- tag
- deploy

Codex 不执行上述操作，除非用户针对该操作明确授权。

交付前可提供：

- 修改文件清单。
- 建议的 commit message。
- CI 需要的环境变量说明。
- 用户应执行的测试命令。

## 6. 新依赖 SOP

新增任何依赖前必须说明：

- 为什么现有依赖无法合理完成任务。
- 官方推荐方案是什么。
- 新依赖会修改哪些 requirements／lock 文件。
- CI 和部署是否需要额外步骤。
- 是否有不新增依赖的替代方案。
- 当前无法运行测试时的风险。

用户批准后才可：

- 修改 `requirements.txt`。
- 更新 lock file。
- 修改 import 和配置。

不得只修改 requirements 而不处理 lock file，也不得手工猜测不兼容的版本。

## 7. 环境变量与 Secret SOP

- Secret 不写入源码。
- 生产 Secret 不写入 `.env` 示例、CI 明文或日志。
- CI 测试可以使用隔离的非生产 Secret。
- 应用读取的变量名称必须与 CI、部署平台和示例文件一致。
- 新增必填变量时，必须同步说明 CI 和部署需要配置什么。
- 安全相关变量缺失时应明确拒绝启动，不使用公开默认值。
- 可选功能的变量不应无故阻止整个 Backend 启动。

## 8. API 与 Response 变更 SOP

改变 Response 前必须检查：

- Pydantic Schema。
- Router 的 `response_model`。
- Service 返回值。
- Interface 声明。
- 前端是否直接读取该字段。
- `null`、缺失值和旧客户端兼容性。

如果字段可能变为 `null`，必须：

- 将后端类型改为 Optional。
- 告知前端需要进行空值处理。
- 不用无关旧资料填补字段来伪装“非空”。

## 9. 数据库与事务变更 SOP

数据库或积分相关工作必须检查：

- Transaction Owner 是谁。
- Repository 是否擅自 commit／rollback。
- 失败时是否可能留下部分资料。
- 并发和重复请求是否安全。
- Ledger、余额缓存和业务状态是否一致。
- 是否需要唯一约束、Migration 和 Rollback Test。

在 Unit of Work 和 Transaction 基础完成前，不应把多步骤流程描述为已经具备
完整原子性。

## 10. 当前协作限制

截至本 SOP 建立时，采用以下默认限制：

- 用户当前无法运行应用或测试。
- Codex 不执行测试，除非用户后来明确改变指示。
- Codex 可进行语法、静态关系和 diff 检查。
- Git 提交与 push 由用户完成。
- 每项修改前必须先解释“为什么”和“怎么改”，并等待确认。

如果限制改变，应以用户最新指示为准，并在交付中说明采用了哪种验证级别。

## 11. 每项任务检查清单

### 修改前

- [ ] 已读取路线图。
- [ ] 已确认 Phase、任务 ID 和依赖。
- [ ] 已检查 Production Gate 与 Design Rules。
- [ ] 已使用代码图检查实现和影响面。
- [ ] 已说明为什么要做。
- [ ] 已说明准备如何修改。
- [ ] 已列出文件、风险和不处理范围。
- [ ] 已取得用户明确确认。

### 修改中

- [ ] 只修改批准范围。
- [ ] 未覆盖用户其他变更。
- [ ] 未泄露 Secret。
- [ ] 未擅自新增依赖。
- [ ] 未擅自修改 API 或数据库契约。
- [ ] 未提前实施其他 Phase。

### 修改后

- [ ] 已执行用户允许的验证。
- [ ] 已检查语法或测试结果。
- [ ] 已执行 `git diff --check`。
- [ ] 已审查 scoped diff。
- [ ] 已准确说明未验证内容。
- [ ] 已提供文件位置和行为解释。
- [ ] 未执行未经授权的 Git 操作。
- [ ] 已说明下一项建议。

## 12. SOP 维护

以下情况应更新本 SOP：

- 用户改变 Git 或测试责任分工。
- 开始使用完整自动化测试。
- 引入新的部署平台或 CI。
- 新增 Migration、Release 或 Rollback 流程。
- 路线图结构发生变化。
- 实际协作中发现遗漏或反复出现的错误。

更新 SOP 本身也应先说明原因和修改范围，并由用户确认。
